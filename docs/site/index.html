Preconfig Toolkit 1.5.1 · engineering overview

Preconfig Generator

The Preconfig Toolkit reads a working EdgeConnect appliance from Orchestrator, turns its configuration into a Jinja2 template and a CSV with one row per site, checks every row against Orchestrator before anything is written, and uploads only what a person approves. It never applies a preconfig. Six commands cover the job (list, build, variables, compare, validate, upload), the same commands run in a local web GUI, and an AI agent can drive them too. validate and upload also take finished YAML files with --yaml.

The problem

Preconfigs are written by hand, one site at a time

A preconfig is the YAML that Orchestrator applies when a new appliance comes online: its interfaces, addresses, routes, BGP, tunnels, NAT and more. For a roll-out of hundreds of branches, someone has to write one per site, and each one must match the reference design exactly.

Before

  • An engineer copies a known-good appliance into YAML by hand, field by field.
  • Each new site is another copy, edited in place: addresses, VLANs, bandwidth, hostnames.
  • Typos and stale fields surface only when the apply fails on site, or worse, when it succeeds wrongly.
  • Nobody can say which fields came from the reference and which were guessed.

With the toolkit

  • The reference appliance is read from Orchestrator, read-only, and converted by code.
  • Site differences become CSV columns; everything else stays fixed in one template.
  • Every row is checked offline, rendered, and sent to Orchestrator's /validate before a file is kept.
  • A ledger accounts for every captured item: carried, owned elsewhere, or outside preconfig.
How it works

Six stages, three gates

Data moves left to right. Blue is the data path; amber marks a gate where Orchestrator or a person must say yes before the next stage runs. Under each stage is the command that runs it: build runs the first two and keeps its folder only if /validate accepts the appliance's own row.

1 · capture

Read the reference appliance

About 110 GET calls per appliance, live and cached copies, secrets redacted before anything touches disk, including passwords typed into banners and notes. list first shows the appliances and whether /validate may run there.

edgeconnect-preconfig list --orchestrator lab edgeconnect-preconfig build --orchestrator lab --appliance Branch-01
2 · translate

Turn it into preconfig YAML

34 section mappers write reference.yaml; every captured item lands in the ledger, nothing is dropped silently. A read that failed is ledgered and nothing is written from it. build runs this step and prints the verdict from summary.md.

(part of build) summary.md: Toolkit 1.5.1 … target ECOS … Verdict: …
3 · variables

Decide what changes per site

A tick list of settings: the Top 10 or Top 20 that differed most between appliances of the same design, or every section. Addresses, serials and secrets are always per site. Or let two or three real sites decide with compare.

edgeconnect-preconfig variables preconfig-output/Branch-01 --pick top10 edgeconnect-preconfig compare preconfig-output/Branch-01 Branch-07 Branch-12
4 · render + check

One file per CSV row

Cells are checked offline (address format, ranges, subnets), each row is rendered and parsed, and mutation tests prove each column changes only its own field.

(part of validate and upload)
5 · /validate

Orchestrator checks every row

A row is written to rendered/ only after the Orchestrator accepts it. Rejected rows are reported; the others continue. It runs only on Orchestrators listed by exact name in EC_VALIDATORS. Finished YAML files are checked with --yaml.

edgeconnect-preconfig validate preconfig-output/Branch-01/site-branch --csv sites.csv edgeconnect-preconfig validate --yaml rendered/
6 · upload

Only with your approval

Rows are validated again and conflicting names or serials are skipped. Without --approve a CSV upload prints the table and sends nothing. upload --yaml checks the files you name and uploads them; uploading is not applying, so it needs no --approve. Every upload has autoApply off.

edgeconnect-preconfig upload preconfig-output/Branch-01/site-branch --csv sites.csv --approve edgeconnect-preconfig upload --yaml rendered/branch-02.yml
Explain more: why a template and a CSV, and not one YAML per site

The output follows the format Orchestrator's own preconfig tooling uses: a Jinja2 template whose placeholders are data['column'], and a CSV whose header names those columns. That keeps the result compatible with pyedgeconnect's generate_preconfig, so a team can keep using its existing tooling.

Splitting the design (template) from the site data (CSV) means the reference is reviewed once, and each new site is one CSV row. The variables.csv sheet records every decision with its reason, so a reviewer can see why a field is per site.

  • Secrets and the hostname are always columns, and the example row never carries a secret value.
  • An address inside the site's own subnet becomes a column; one equal to an interface address is linked to that column, so the gateway follows the interface.
  • Values are written through | tojson, so a ZIP code like 08034 or a route target like 1:1 stays a string.
Local web GUI · since 1.4.0

The same commands, in a browser

edgeconnect-preconfig gui runs on this computer only (127.0.0.1) and drives the command line's own code, so every check and result is the same. Build a template from an appliance, tick the settings that change per site beside reference.yaml, then make, validate and upload the files. Uploads stay off for an Orchestrator until <nickname>_gui_preconfig_uploads=on is in .env, and the GUI never applies a preconfig.

edgeconnect-preconfig gui # opens your browser; Ctrl+C stops it edgeconnect-preconfig gui --port 8765 --no-browser # a fixed port; prints the sign-in link instead

Explain more: how the toolkit decides

Translate reads the template groups associated with the appliance. When a selected template has the same name as a preconfig section (with one alias: the peerPriorityList template provides peerPriority), the section is not written and the ledger says template-group. Writing it anyway would make the preconfig and the template fight over the same settings. Template settings that do not apply to the appliance (route targets, a VXLAN VTEP) are still written, NAC under a merge template is handled, and when the groups' templates cannot be read, every section a template could provide is withheld instead of guessed.

Objects Orchestrator creates for overlays and cloud services carry a gms_marked flag. Every mapper skips them and records them as orchestrator-managed, so a cloned site does not get a second copy of Orchestrator's own tunnels.

Since 1.3.0 a preconfig holds only key paths that the target release's default template has, plus a short list of known omissions from that template. Each path left out is one outside-preconfig ledger line. The template is picked by release family: the exact build, else the newest of the same major.minor, else the nearest older (untested), else the nearest newer. A template downloaded from an Orchestrator goes to the work folder.

How it judges its own output

Every captured item lands in exactly one bucket

The ledger records a disposition for every endpoint and decision. summary.md groups them the way a report reads them and ends with one verdict line, judged against what the preconfig format can express, never against the whole appliance.

MappedCarried into the YAML. Some on a stated assumption the owner confirms.
GapThe format has a place for it, the value was not carried. The only real defect.
Toolkit errorA mapper could not read the data. Reported as a bug, never as a limit.
Not readableThe format has a place for it, but it could not be read: business hours (POST only), a read the API key's roles refused (HTTP 403), or a read that failed or came back malformed. Nothing is written from it. Check by hand.
Owned elsewhereTemplate group or Orchestrator-managed, as intended.
Outside preconfigNo section or field for it in the target release. Set another way.
Toolkit: 1.5.1 (commit …, 2026-11-06) · written for Orchestrator 9.7.1 · target ECOS stated
Verdict: Incomplete for preconfig: N gap(s), 0 toolkit error(s).
Explain more: what the verdict means, and why the version is on the first line

A YAML is complete when it carries every value the preconfig format can hold. An appliance with firewall rules and hub roles can still be complete for preconfig, because those belong to template groups and Orchestrator overlays. Before this rule, an agent called a correct YAML "not faithful" because of items preconfig has no place for.

The first line also states which target ECOS the translation used. An earlier example, from a KVM lab appliance built with 1.2.3 on 2026-10-23, had four gaps: a NAC policy on a sub-interface with no LAN label, the rest of NAC (the validator answers HTTP 500 when any of its six lists is empty), a licensing tier name that is not documented, and two extra remote DHCP pools the validator will not take as a list. Business hours are listed under Not readable.

A failed or malformed read never stops the run and never becomes an empty list or a false default; nothing is written from it. A list item that cannot be read is skipped and ledgered on its own. A read the API key's roles refuse (HTTP 403) does not stop the run either: it is recorded, and summary.md lists it under Not readable with a note to check those sections by hand or widen the key's read roles. The one exception is the routes read, because a preconfig without its routes would be wrong; that stops the capture.

The toolkit version and commit sit on the first line because a gap reported from an old toolkit may already be fixed. A toolkit with local edits is flagged, since its results are not trustworthy; a default template the toolkit cached for a new release does not count as an edit.

Safety model

Built so nothing reaches an appliance by accident

GET-only reads

Capture only reads. Reference Orchestrators are read-only; a script stops if its client ever counts a write where none is allowed.

Secrets never stored

Passwords, keys and PSKs become <SECRET:path> before anything is written, and so do credentials in free text such as banners and notes, in the documented phrasings. The example row never holds a secret.

Every row validated

A file is kept only after Orchestrator's /validate accepts it. A bad row is skipped; the rest carry on.

Uploads are gated

A CSV upload needs the explicit --approve flag. upload --yaml sends only the files you name, after the same checks, and refuses any file that still holds a <SECRET:…> placeholder. Conflicting names or serials are skipped.

Agents show every command

An agent shows the exact command for each step, ready to paste, and never edits the toolkit; it names gaps instead.

Certificates pinned by fingerprint

A self-signed lab Orchestrator is trusted by its SHA-256 fingerprint, never because of its profile name.

Nothing applies

The toolkit cannot apply a preconfig, now or later: every upload has autoApply off, and a test fails if any script or test calls the apply API. A person applies it in Orchestrator.

Validators named exactly

/validate runs only on Orchestrators listed by exact nickname in EC_VALIDATORS. A name is never allowed for what it contains, and with none listed, none is allowed.

Testing philosophy

Trust Orchestrator's behaviour, not its documentation

Every rule in the toolkit was found by asking the real system. Swagger descriptions and template comments were treated as hints: 21 template comments name keys that the validator does not accept.

Evidence first

Before a mapper is written, the field is read from real captures across releases and the default template's actual YAML keys. Behaviour is probed on the validator, not assumed.

Close the loop

Apply the generated preconfig to a lab appliance, capture it again, translate it again, and compare every value. /validate accepting a file proves the syntax, not the result.

A test that fails first

Every fix ships with a test that was seen failing on the old code. A test that never failed proves nothing.

Someone else checks

Independent reviewers see only the request and the diff, never the author's reasoning, and try to break the change. Findings are fixed and re-reviewed: 12 rounds before the 1.3.0 pushes, and a review again for 1.3.2.

Unit tests. 738 at 1.5.1, offline, run before every push and in CI on Python 3.9 and 3.13, on Linux, macOS and Windows (WSL), plus the GUI in three browsers: redaction, GET-only, YAML 1.2 parsing, mappers, ledger classification, the no-apply rule, exact validator names, and a check that every .env key the code reads is documented in .env.example.

Options, mutation and fuzz. Every documented enum, range and boolean in the default template, one at a time, against the validator. 3,160 mutated captures from 40 seeds check that a bad read never makes a run fail as a whole, and every new guard line or check is mutation-tested (44 of 44 caught in the 1.3.0 round).

Corpus. Every real appliance translated, mutated and validated, from ECOS 9.3.1 to 9.7.2 and nine hardware and virtual models. Every change is run over 913 to 987 real captures, and the YAML may change only where intended.

Validator. What /validate really checks, probed directly: object names, release-specific fields, minimal documents.

Live apply and diff. Generated preconfigs applied to the KVM lab through the Orchestrator API, re-captured and compared leaf by leaf, in the API and the CLI running-config. For 1.3.0: 37 source appliances, 10 batches, 53 comparisons, 231,352 differences classified, management access intact after every apply. For 1.3.2: 10 appliances in 2 batches, all applied with every step passing.

Experiments. Controlled A/B tests on the lab to settle a single question, then cleaned up and verified by read-back.

How we reached each conclusion

Case studies

Each rule in the toolkit has a story: a question, an experiment, the evidence, and the conclusion that went into code and tests.

An empty tunnel list could remove a site's tunnels

data loss avoided
Question

What does the converter write when no passthrough tunnel can be mapped?

Experiment

A unit test fed one tunnel the mapper could not read and looked at the section written.

Evidence

It wrote tunnelConfiguration: {tunnels: []}. That section replaces on apply, so an empty list asks Orchestrator for no tunnels.

Conclusion

No section is written when no tunnel maps, and the unreadable tunnel is reported as a toolkit error. Test added; found during a requested review.

A route without a next hop passes /validate and fails at apply

validate ≠ apply
Question

Does a route that names only an interface survive a real apply?

Experiment

A lab apply carried an interface-only route on an interface that no longer existed.

Evidence

/validate accepted the file; the apply's routes step failed. Separately, routes with next hop 0.0.0.0 show an empty next hop in their state but keep it in their config.

Conclusion

Routes with no next hop are left out and recorded in the ledger; 0.0.0.0 routes are read from their config, so they are kept correctly.

A null segment turned BFD on

found by live apply
Question

Is segment: null in a preconfig the same as leaving the segment out?

Experiment

A cloned site was applied to a lab appliance, captured again and compared with its source.

Evidence

After the apply, BFD was on in the Default segment, which the source never had.

Conclusion

The toolkit never writes segment: null. The gap-fix batch proved the fix live.

A route interface that does nothing

release difference
Question

Does a route with next hop 0.0.0.0 or :: need the interface it names?

Experiment

Live applies to virtual appliances on ECOS 9.6.2.1 and 9.7.1.0, with and without the interface.

Evidence

ECOS 9.7 and later reject the route with an interface, and the whole routes step fails. On earlier releases the interface has no effect. Without an interface, ECOS ignores the zone and shows it as none.

Conclusion

Since 1.3.2 these routes are written without the interface, for every source and target ECOS. --target-ecos is still accepted and recorded, but no longer changes routes.

Disabled NAC that wasn't

found in field use
Question

Why would a preconfig fail with "NAC - server key can not be empty" when NAC is switched off?

Experiment

Captured appliances were checked for NAC that is off and holds only factory-default objects.

Evidence

16 of 75 had it, on ECOS 9.5, 9.6 and 9.7: NAC off, the default server 0.0.0.1, no key. The section was still written, with a RADIUS key column to fill.

Conclusion

Since 1.3.2 that NAC is left out. Enabled or set-up NAC is still written, and an empty key cell is refused before /validate. Live, each appliance kept its own NAC.

IDS/IPS would have been switched off on every clone

security
Question

Where does an appliance's IDS/IPS mode come from?

Experiment

The audit read the mapper and the API; all four modes were applied live and read back.

Evidence

The first version always wrote mode: Off. The section replaces on apply, so every clone would lose IDS/IPS.

Conclusion

The mode now comes from Orchestrator's IDS state. An appliance missing from that state is a gap, and the section is not written.

A NAT map listed by name only means no rules

root cause
Question

Why do some appliances answer {"map1": "map1"} instead of rules, and does release 9.7 keep rules elsewhere?

Experiment

On a 9.6.2.1 and a 9.7.1 lab appliance: add one disabled test rule, read every NAT path, apply an empty rule list, read again.

Evidence

Rules appear, then the map shrinks back to its bare name on both releases, on every read path. The lab's reset step applied exactly that empty list.

Conclusion

Names-only means a map with no rules. The live copy is read first, because Orchestrator's cache lags right after an apply.

The order of linkAggregation in the YAML does not matter

A/B proven
Question

Must the bond section come before deploymentInfo for an interface on the bond to work?

Experiment

Stored two preconfigs and read them back; then applied a test bond with a LAN interface on it, section first and section last.

Evidence

Orchestrator stores the YAML unchanged, and in both orders applies link aggregation before deployment. Both applies completed with the interface up.

Conclusion

No reordering needed. Side finding: an empty bond list never deletes a bond; it is removed on the appliance.

YAML 1.1 turned route targets into numbers

silent corruption
Question

Do all values survive a round trip through YAML?

Experiment

Corpus run over real appliances with BGP route targets, ZIP codes and yes/no strings.

Evidence

The default parser read 1:1 as the number 61, yes as true, and crashed on 08034.

Conclusion

A strict YAML 1.2 parser everywhere, and every string rendered through tojson.

Release 10.0 sends its default template differently

new release
Question

Why did translate fail on an Orchestrator on 10.0.0.40625?

Experiment

Read the default-template endpoint on that release.

Evidence

It answers JSON with the YAML base64-encoded in configData, where earlier releases answer plain YAML.

Conclusion

Capture decodes and checks it before caching, and translate names the cached releases when one is missing.

280 rejections
Question

What does Orchestrator's validator actually check?

Experiment

20 targeted probes and 473 option cases, then live applies of accepted files.

Evidence

It checks the YAML against the release's schema and that named objects exist on that Orchestrator. Some accepted files still fail at apply.

Conclusion

Known apply-time failures are caught before /validate, and the live apply-and-diff loop became the real proof.

Use it

From install to a validated site file

Install

bash <(curl -fsSL https://raw.githubusercontent.com/mirwasay/edgeconnect-preconfig/main/install.sh)
  1. install.sh installs this repository: the edgeconnect-preconfig command and its agent skill. To pick from all three EdgeConnect repositories, run install-all.sh from the same place instead; the old setup.sh still works and runs it.
  2. Pick your agents once; the skill is installed for them. Run the script again to update.
  3. Fill in .env as the last screen shows: Orchestrator nickname, address and API key, and EC_VALIDATORS with the nicknames /validate may run on. .env.example lists every key and the values it accepts.

Run

  1. list the appliances, then build from the reference one and read summary.md: version, target ECOS, groups, verdict. --target-ecos is optional; it is recorded and no longer changes routes.
  2. Choose the per-site settings with variables, or let two or three sites of the same design choose with compare.
  3. Fill one row per site in sites.csv, starting from <hostname>.csv (headers only) or example.csv (this appliance's values, secrets blank), then validate.
  4. Run upload to see the table, then again with --approve once it is right.
  5. Have finished YAML files? validate --yaml FILE|FOLDER only checks them; upload --yaml FILE|FOLDER checks and uploads them, with autoApply off.

Ask an agent

"Build a preconfig template from Branch-01 on the lab Orchestrator, compare it with Branch-07 and Branch-12, and give me the commands."

The agent runs the read-only steps, shows each command in its own block, reports the verdict from summary.md, and hands the upload command back to you. It asks for the target ECOS, leads with any "Warning: apply will fail", and lists the route labels and interfaces the target must have.

Glossary

Terms used on this page

Preconfig

YAML that Orchestrator applies to an appliance when it is approved or comes online.

Reference appliance

A working appliance whose configuration is the design for a site type.

Site type

One template plus a CSV with a row per site of that kind.

Ledger

The record of every captured item and what happened to it.

Template group

Orchestrator templates applied to many appliances; they own some sections.

/validate

Orchestrator's check of a preconfig without saving it.

EC_VALIDATORS

The .env list of Orchestrator nicknames /validate may run on, matched exactly.

Apply-and-diff

Apply in the lab, capture again, translate again, compare every value.

gms_marked

Flag on objects Orchestrator created itself; never copied into a preconfig.

KVM Lab Orchestrator

The lab with five virtual appliances, on ECOS 9.6.2.1 and 9.7.1.0, where cloned sites are applied and compared.

Test Lab Orchestrator

A multi-tenant lab Orchestrator, read-only, source of reference configurations.

Field reference appliances

Real appliances, captured read-only, to check the converter on live configurations.

Virtual Lab Orchestrator

The lab Orchestrator used for conversion runs and validation.

Target ECOS

The ECOS release of the appliances that will get the preconfig, given with --target-ecos. Recorded in the summary; since 1.3.2 it no longer changes routes.
